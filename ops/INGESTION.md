# Ingestion contract — `POST /ingest`

This is the seam the connectors write to. Hermes (`ui/server/hermes.mjs`) owns
the household context store, and `/ingest` is the only supported write path.
Hermes is also the store's **sole deleter**: retention, purge, and
reconciliation happen through the bearer-only `/admin/*` routes documented
below, never by another process opening the database.

**There is no read path for corpus content.** `/search` and `/recent` were
removed. Nothing over HTTP returns a context row, and the assistant's browser
bundle can no longer request one. Retrieval becomes an in-process call owned by
a sealed reader (`handleVaultAsk` in `ui/server/hermes.mjs`, served at
`POST /vault/ask`) that composes an answer and returns
speech, never rows. (`GET /admin/entities` returns entity *ids and timestamps*
for reconciliation — deliberately never text or meta.)

Everything below was exercised against a running Hermes on 2026-08-12, and the
schema-v2 upsert and `/admin/*` sections again on 2026-08-19 (isolated port
8799, throwaway DB, test credentials). Response bodies are copied from those
runs, not paraphrased.

## Endpoint

```
POST http://localhost:8789/ingest
```

`HERMES_PORT` moves the port; `HERMES_DB` moves the database file;
`HERMES_TOKEN_FILE` moves the bearer token. Hermes binds loopback only — there is
no remote listener to point at, so ingestion must run on the same machine.

Start it from `ui/` with `npm run hermes`.

## Authentication — this is new, and it will break an existing caller

Every route except `GET /health` now requires an authorized caller. There are two
channels and one gate:

| Channel | How | Who uses it |
|---|---|---|
| **bearer** | **No `Origin` header**, plus `Authorization: Bearer <token>` | curl, launchd, the connectors |
| **browser** | An `Origin` header that is present and allowlisted | nothing in the shipped product today — the widget is a native bearer client; the default allowlist still admits the deleted Expo app's dev origins (`DEFAULT_ALLOWED_ORIGINS` in `ui/server/hermes.mjs`) |

The `/admin/*` lifecycle routes accept **only the bearer channel** — the browser
channel gets a 403 that says so (see the Lifecycle section below).

The token is 64 lowercase hex characters in an owner-only file, generated by
`ops/setup-llm.sh` at `~/.hazlie/secrets/hermes-token.txt` (mode `0600`, inside a
`0700` directory — Hermes refuses to read it otherwise, and refuses to start
without it). Read it from the file at call time rather than copying it anywhere;
rotation is `rm` plus a re-run of `setup-llm.sh`, and Hermes picks up a new value
without a restart.

**What changed and why.** A missing `Origin` header used to be *trusted*, which
meant any local process could write the household's context store by simply not
sending one — and that store feeds what the assistant says. The token is what
makes an Origin-less caller legitimate rather than merely unidentified.

**The residual gap, stated plainly so "authenticated" does not imply more than it
delivers:** a same-machine process running as a *different* uid can send
`Origin: http://localhost:8081` and reach the browser channel without knowing the
token. That is strictly smaller than what it replaces (which needed no forgery at
all, and additionally admitted any web page the household happened to have open),
and `~/.hazlie` is `0700` so such a process cannot read the database directly
instead. A process running as *your own user* is out of scope by construction: it
can read the token file and the database, and no server-side check changes that.
The machine is still the security boundary.

## Request requirements

| Requirement | Rule | Failure |
|---|---|---|
| Method | `POST` | 404 on other paths/methods |
| Authorization | bearer token, or allowlisted `Origin` | **401** |
| `Content-Type` | exactly `application/json` | 415 |
| Body size | ≤ 1 MiB | **413** |

The media type is matched on its essence, so `text/plain; x=application/json` is
rejected (verified). That is deliberate: `text/plain` is CORS-safelisted, and
accepting it would let any web page the household visits fire a no-preflight POST
into the context store.

The browser allowlist defaults to `http://localhost:8081` and
`http://127.0.0.1:8081`; `HERMES_ALLOWED_ORIGINS` replaces the list.

## Row schema

Send one object or an array of objects.

| Field | Type | Required | Notes |
|---|---|---|---|
| `source` | non-empty string | **yes** | Provenance label, e.g. `granola`. |
| `text` | non-empty string | **yes** | The content. This is what FTS5 indexes. |
| `ts` | finite number | no | Epoch **milliseconds**, truncated to an integer. Defaults to server `Date.now()`. **Always supply it on entity rows** — a defaulted `ts` changes the content hash on every delivery, turning each redelivery into a spurious update. |
| `speaker` | string or `null` | no | See the constraint below. |
| `meta` | any JSON | no | Stored as a JSON string. Nothing reads it back over HTTP any more. |
| `entity_id` | non-empty string or `null` | no | Stable logical identity for the row; makes redelivery an **upsert**. See the contract and registry below. |

### The `speaker` constraint — do not design around this

`speaker` is **ingest-supplied text attribution**: a label that arrives with the
row, exactly like `source`. Nothing in this codebase derives it from audio, and
nothing may. No voiceprints, no enrollment, no cross-session identification of a
voice — the assistant's own identity surface stays ephemeral per session. This is
the BIPA line described in the project README, and it binds the ingestion side
too. If your pipeline can supply a name because a human typed it or a calendar
said so, that is fine. If it would supply a name by recognizing a voice, that is
the thing we are specifically not building.

## Batch semantics

Validation runs over the whole batch before anything is written, inside a
transaction. One bad row rejects the entire batch and writes nothing — verified:
a two-row batch whose second row had no `source` returned

```json
{"error":"ingest[1]: missing \"source\" string"}
```

and left the row count unchanged. The error names the failing index, so retry
whole batches rather than tracking offsets.

**The dedup question is resolved (schema v2): rows carrying an `entity_id` are
idempotent by upsert.** Re-POSTing an identical entity batch changes nothing and
says so (`unchanged`); a retry after a lost response is free. Rows *without* an
`entity_id` still insert on every POST — for those, the caller still owns
at-most-once (high-water mark, cursors). Sources with a natural identity should
send one; the contract is the next section.

## Entity identity and the upsert contract — schema v2

A row MAY carry `entity_id`, a stable logical identity. For those rows `/ingest`
upserts inside the batch transaction:

| Hermes already holds this `entity_id`? | Content hash | Effect | Counted as |
|---|---|---|---|
| no | — | row inserted | `inserted` |
| yes | equal | nothing written, no FTS churn | `unchanged` |
| yes | different | `ts`, `speaker`, `text`, `meta` replaced **in place**; latest wins | `updated` |

`entity_id` is globally UNIQUE (partial index, `WHERE entity_id IS NOT NULL`);
rows without one never collide with anything. An update keeps the row's `id` and
`source`, and the FTS index follows automatically (the `context_au` trigger).

### The canonical content hash — computed server-side, and only there

Hermes decides "changed vs unchanged" with `content_hash`: sha256 over a
canonical serialization of `{ts, speaker, text, meta}` — object keys sorted
recursively, `null`-valued and missing fields normalized to the same absence,
`meta` canonicalized as the parsed JSON value rather than whatever string the
client serialized. **Do not compute or send a hash from the connector side**;
there is deliberately no field for it. A second implementation would eventually
disagree on serialization, and every redelivery would become a spurious update —
or a real edit would be dropped as unchanged.

One rule binds connectors: **arrays keep their order in the hash.** A generic
canonicalizer cannot know which arrays are really sets, so a connector must
pre-sort semantically-unordered arrays (attendees, recipients, categories)
before ingest — otherwise a reordered attendee list reads as an edit. Verified:
a redelivery with `meta` *object keys* reordered at every depth landed as

```json
{"inserted":0,"updated":0,"unchanged":1}
```

### Entity id registry

One namespace per source, colon-separated, so ids cannot collide across
sources and a human can read provenance off the id:

| Source | `entity_id` format | Notes |
|---|---|---|
| `imessage` | `imessage:<guid>` | chat.db message GUID. |
| `calendar` | `calendar:<event_uid>:<recurrence_id>` | Stable event UID + recurrence identity from the probed schema; occurrence-start fallback ONLY if the probe finds no UID column (recorded in `ops/PROBES.md`). |
| `mail` | `mail:<Message-ID>` | Message-ID normalized: trimmed, enclosing `<>` stripped, host part lowercased. Fallback when absent: `mail:<account>:<folder>:<uidvalidity>:<uid>`. |
| `granola` | `granola:<note_id>` | |
| `health` | `health:<metric>:<YYYY-MM-DD>` and `health:workout:<start_iso>` | One row per metric per completed local day; upsert lands corrections. |
| `notes` | `notes:<note_id>` | Apple Notes primary key. |
| `photos` | `photos:<uuid>` | Photos library asset UUID. |
| `notion` | `notion:<page_id>` | |
| `files` | `files:<absolute path>` | The path is the identity. |
| `whatsapp` | `whatsapp:<stanza_id>` | |
| `linkedin` | `linkedin:conn:<slug>` and `linkedin:msg:<sha8>` | Export seed: slug from the profile URL (hash fallback); messages keyed by a hash over conversation/date/sender/content. |
| `hazlie_digest` | `hazlie_digest:<date>` | Reruns replace the day's digest. |
| `seed` | (none) | Dev fixtures stay unkeyed; re-seeding inserts again by design. |

This table went stale once already (it was missing six live sources when the
2026-08-22 audit read it). The list a doc cannot drift from is hermes' own
`KNOWN_SOURCES` (`ui/server/hermes.mjs`); the per-source row shapes live in
[`CONNECTORS.md`](CONNECTORS.md)'s source registry.

Verified round trip (2026-08-19): first delivery of a two-row entity batch →
`{"inserted":2,"updated":0,"unchanged":0}`; the identical batch again →
`{"inserted":0,"updated":0,"unchanged":2}`; the same calendar entity with
edited text and times → `{"inserted":0,"updated":1,"unchanged":0}`.

A malformed `entity_id` rejects the whole batch like any other bad row —
verified:

```json
{"error":"ingest[1]: \"entity_id\" must be a non-empty string"}
```

## Responses

| Code | Body | Meaning |
|---|---|---|
| 200 | `{"inserted":2,"updated":0,"unchanged":0}` | All three upsert outcomes, per batch. `inserted` = new rows; `updated` = entity rows replaced in place; `unchanged` = redeliveries the canonical hash proved identical. |
| 400 | `{"error":"ingest[1]: ..."}` | Bad row; nothing written. |
| 401 | `{"error":"unauthorized"}` | No bearer token, or an `Origin` that is not allowlisted. |
| 413 | `{"error":"request body too large"}` | Over 1 MiB; split the batch. |
| 415 | `{"error":"content-type must be application/json"}` | Wrong media type. |

413 is a real, readable response rather than a dropped connection (verified at
2 MiB and 4 MiB), and the connection stays reusable afterwards — so a client can
distinguish "split the batch" from "Hermes is down, retry later". Past 8 MiB
Hermes stops draining and hangs up; at that point a reset is the honest answer.

401 is returned uniformly rather than distinguishing "bad token" from "origin not
allowlisted" — telling those apart would report the contents of the allowlist to
whoever asks.

## Working example

```bash
TOKEN=$(cat ~/.hazlie/secrets/hermes-token.txt)

curl -X POST http://localhost:8789/ingest \
  -H 'Content-Type: application/json' \
  -H "Authorization: Bearer $TOKEN" \
  -d '[
    {"source":"granola","text":"minimal row"},
    {"ts":1754000000000,"source":"granola","speaker":"parent",
     "text":"full row with meta","meta":{"room":"kitchen"}}
  ]'
# {"inserted":2,"updated":0,"unchanged":0}
```

Without the header, verified:

```bash
curl -X POST http://localhost:8789/ingest \
  -H 'Content-Type: application/json' \
  -d '{"source":"x","text":"y"}'
# {"error":"unauthorized"}     [401]
```

## Checking that it worked

```
GET /health          -> {"ok":true}          no auth, no row count
GET /stats           -> {"rows":2}           requires auth
```

`/health` deliberately no longer reports `rows`: it is a monotone counter over a
household audio corpus, so serving it unauthenticated reports when the house is
talking without disclosing a single word. `/stats` is the authenticated
replacement, and it is now the only way to observe that a write landed.

The removed routes answer 410, not 404, so a stale caller gets told rather than
guessing at a typo — verified:

```
GET /search?q=row    -> 410 {"error":"GET /search was removed: corpus rows no
                             longer cross into the browser. Retrieval moves
                             in-process to the sealed reader (POST /vault/ask)."}
GET /recent?limit=3  -> 410 {"error":"GET /recent was removed: corpus rows no
                             longer cross into the browser."}
```

The FTS index is still a shadow of `context.text` maintained by SQLite triggers,
so rows written by *any* path — `/ingest`, the seed script's direct-DB fallback,
or `sqlite3` at a prompt — are searchable by the in-process reader without extra
work.

## Lifecycle — the `/admin/*` routes (bearer channel ONLY)

Hermes is the sole deleter of the context store; connectors *request* retention
here instead of touching the database. Every admin route refuses the browser
channel outright — verified with an allowlisted `Origin`:

```json
{"error":"admin routes are bearer-only: deletion is not a browser capability. Call with the token from ~/.hazlie/secrets/hermes-token.txt and no Origin header."}     [403]
```

Every operation that names a source validates it against the closed allowlist
in `KNOWN_SOURCES` (`ui/server/hermes.mjs`). A typo'd source would otherwise
"succeed" by deleting zero rows — re-captured live 2026-08-22 against the
running hermes:

```json
{"error":"unknown source \"notez\"; valid sources: imessage, calendar, mail, granola, health, photos, notes, files, notion, linkedin, whatsapp, hazlie_digest, seed"}     [400]
```

The previous capture here used `notes` as its example of an INVALID source, and
`notes` has since become a valid one — so the block was teaching the opposite of
what it meant. The allowlist is deliberately not restated in this file any more:
it has grown twice since this page was written, and a list copied into prose is
a list that goes stale. Read it from `KNOWN_SOURCES`.

Request bodies are closed field sets: an unknown field is a 400 that names what
the route accepts, never a silently ignored key — verified with `keepDays`
(camel-cased) instead of `keep_days`:

```json
{"error":"unknown field \"keepDays\"; this route accepts: source, keep_days"}     [400]
```

### `POST /admin/retain {source, keep_days}`

Deletes rows of `source` older than `keep_days` days (integer, 1–3650).
Verified — one year-old `mail` row against `keep_days: 90`:

```json
{"deleted":1}
```

Retain deletes cheaply and leaves the physical cleanup to a scheduled
`/admin/maintain` (below).

### `POST /admin/purge {source}`

Deletes ALL rows for the source, then **immediately** runs the FTS rebuild and
`VACUUM` inline. FTS5's delete path writes only a tombstone — the text stays
legible in the index's own pages until a rebuild rewrites them, and the freed
pages are only zeroed by `VACUUM` under `secure_delete` — and a purge of
sensitive data must physically clean *now*, not at the next maintenance window.
Verified after ingesting two `granola` rows:

```json
{"deleted":2,"maintained":true}
```

(The test suite additionally asserts the purged text is absent from the
database *file* afterwards, not just from FTS matches.)

### `POST /admin/delete-entities {source, entity_ids}`

Reconciliation deletes: 1–500 entity id strings per batch, and a row is deleted
only when `source` AND `entity_id` **both** match — ids are namespaced by
convention, not constraint, so a crossed-up id list cannot delete another
source's rows. Verified:

```json
{"deleted":1}
```

### `GET /admin/entities?source=&from_ts=&to_ts=`

The read half of reconciliation, and deliberately the only thing it can read:
**entity ids and timestamps, never text or meta** — corpus content crossing
back here would land in the connector process, whose logs and state files are
outside the corpus boundary. Upserts cannot express deletion, so after a window
scan the connector fetches Hermes' ids for the window, diffs against what it
observed, and calls `delete-entities` for the difference (a rescheduled
calendar event moves; a cancelled one disappears). Verified:

```json
{"entities":[{"entity_id":"calendar:ABC-123:20260819T170000Z","ts":1755000000000}]}
```

`from_ts`/`to_ts` are optional epoch-ms bounds (unbounded when omitted). The
response is capped at 5000 entities; above the cap the route answers a 413
telling the caller to narrow the window — a silently truncated list would read
to a reconciler as "these entities no longer exist", and it would delete the
remainder.

### `POST /admin/maintain {}`

The batched physical cleanup: FTS rebuild + `VACUUM`. Verified:

```json
{"maintained":true}
```

**`VACUUM` blocks Hermes for its whole duration** — every `/ingest` and lane
request queues behind it — so schedule this in an idle window (the connectors
daemon defaults to 03:30), not after every retention pass.

## The model routes, for completeness

Not part of ingestion, but they moved in the same change and a stale caller will
notice:

```
POST /v1/chat/completions             -> 410, names the replacement
POST /lane/local/v1/chat/completions  -> proxied to llama-server
POST /lane/cloud/v1/chat/completions  -> 501 {"error":"the cloud lane is not built"}
```

A model call has to name its lane. There is deliberately no unlaned alias: an
alias would be exactly the implicit default the lane split exists to remove.

## Storage

Default `~/.hazlie/context/context.db`, file mode `0600` inside a `0700`
directory (verified). Hermes refuses to open a database whose parent directory is
not `0700` rather than silently loosening permissions on it. The DB lives in
private runtime state, never inside the checkout, and `data/` is gitignored.

Three PRAGMAs are set on every connection so that "deleted" means deleted:
`secure_delete = ON` (zero freed pages instead of leaving the text legible in the
free list), `journal_mode = DELETE` (no `-wal`/`-shm` sidecar holding the same
text at a mode nothing asserts), and `temp_store = MEMORY`. Because
`secure_delete` only applies to pages freed *after* it is enabled, opening a
database at `user_version` 0 also runs a one-time `VACUUM` to rewrite existing
pages. The schema is now at `user_version = 6`: opening an older database
migrates it in place, version by version, with existing rows preserved. In
brief — v2 added `entity_id` and `content_hash` plus the partial UNIQUE index
that turns redelivery into an upsert (pre-v2 rows keep a `NULL` `entity_id`);
v3 added the `store_changed_at` ingestion cursor and FTS5 secure-delete on
both indexes; v4 rebuilt `claim_fts` with the porter stemmer; v5 rescoped
entity uniqueness to `(source, entity_id)`; v6 added the
`context_source_ts (source, ts, entity_id)` index for per-source time-range
reads. The version-history comment above `SCHEMA_VERSION` in
`ui/server/hermes.mjs` is the authoritative list.

## Not provided

No TLS, no remote binding, and no rate limit. All are deliberate for a
loopback-only personal-device service; all would need revisiting before this
ran anywhere multi-tenant. Deduplication and purge/retention, both previously
on this list, now exist: entity upsert (above) and the `/admin/*` lifecycle
routes, which honor the required order `DELETE` → `INSERT INTO
context_fts(context_fts) VALUES('rebuild')` → `VACUUM` — inline for purge,
scheduled via `/admin/maintain` for routine retention.
